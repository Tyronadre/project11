# SQL cheatsheet

Examples target **H2 2.x**, the embedded database used by this app. Most SELECT/INSERT/UPDATE/DELETE syntax also works in other relational databases; date, identity, and backup syntax can differ.
Use a separate practice database for exercises. Never store a plaintext password in `app_users`.

## Open a local SQL shell

First cache/copy the H2 tools while online:

```powershell
.\gradlew.bat copyDatabaseTools
```

The task copies the resolved H2 JAR into `build/tools/`. Keep it for offline use.
**Stop the Spring Boot app before opening its embedded database in another process.**

From the project root, PowerShell:

```powershell
$h2Tool = (Get-ChildItem -LiteralPath build/tools -Filter 'h2-*.jar' | Select-Object -First 1).FullName
java -cp "$h2Tool" org.h2.tools.Shell -url 'jdbc:h2:file:./data/project11;IFEXISTS=TRUE' -user sa
```

This command uses the empty password of the local learning configuration.
For a database with a password, launch the interactive connection prompts instead of putting the password in a command:

```powershell
java -cp "$h2Tool" org.h2.tools.Shell
```

At the prompts, enter the database URL above, the H2 driver (`org.h2.Driver`), and the configured DB username/password.
`IFEXISTS=TRUE` prevents accidentally creating an empty database at the wrong location.

Linux / macOS:

```bash
java -cp 'build/tools/*' org.h2.tools.Shell \
  -url 'jdbc:h2:file:./data/project11;IFEXISTS=TRUE' -user sa
```

For password-protected databases on Linux, omit `-url` and `-user` too and use the interactive prompts.

For a **separate disposable practice database**, use `jdbc:h2:file:./data/sql-practice` instead, without `IFEXISTS=TRUE`.
The shell's `help` lists commands; `exit` leaves it. Terminate SQL statements with semicolons.
No browser console or database TCP server is enabled in this app. The [H2 tutorial](https://h2database.com/html/tutorial.html) documents its local tools.

## Inspect the schema

```sql
SHOW TABLES;
SHOW COLUMNS FROM app_users;

SELECT column_name, data_type, is_nullable
FROM information_schema.columns
WHERE table_name = 'APP_USERS'
ORDER BY ordinal_position;
```

H2 normally stores unquoted identifiers in uppercase in metadata. SQL keywords and unquoted table/column identifiers are case-insensitive.
String data comparisons are a separate matter; the app lowercases email before storage.

Equivalent SQL for the schema generated from `AppUser` (for reference; do not maintain a separate schema script):

```sql
CREATE TABLE IF NOT EXISTS app_users (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    display_name VARCHAR(80) NOT NULL,
    email VARCHAR(254) NOT NULL,
    password_hash VARCHAR(100) NOT NULL,
    created_at TIMESTAMP WITH TIME ZONE NOT NULL DEFAULT CURRENT_TIMESTAMP,
    is_admin BOOLEAN NOT NULL DEFAULT FALSE,
    tally_count INTEGER NOT NULL DEFAULT 0,
    CONSTRAINT ck_app_users_tally_nonnegative CHECK (tally_count >= 0),
    CONSTRAINT uk_app_users_email UNIQUE (email)
);
```

| Type / constraint | Meaning |
| --- | --- |
| `BIGINT` | Large whole number; appropriate for IDs |
| `VARCHAR(n)` | Text up to n characters |
| `BOOLEAN` | True/false |
| `DECIMAL(10,2)` | Exact decimal, up to 10 digits total and 2 after the point |
| `DATE` | Calendar date |
| `TIMESTAMP WITH TIME ZONE` | Date/time with timezone offset information |
| `PRIMARY KEY` | Unique, non-null row identity |
| `GENERATED ... AS IDENTITY` | Database supplies an ID when omitted |
| `NOT NULL` | A value must exist; does not itself forbid empty strings |
| `UNIQUE` | Prevent duplicate values; NULL behavior varies by database |
| `DEFAULT` | Value used when the column is omitted on INSERT |
| `CHECK (...)` | Enforce a row condition |
| `FOREIGN KEY` | Require a referenced row to exist |

Avoid floating-point types for exact money amounts. Store a currency alongside monetary values.
Use single quotes for text (`'Alex'`). Double quotes delimit exact identifiers (`"MixedCase"`), which are usually unnecessary here.
Escape a literal apostrophe with another apostrophe: `'O''Brien'`.

## Read, create, update, delete

Read users without exposing hashes:

```sql
SELECT id, display_name, email, created_at
FROM app_users
ORDER BY created_at DESC, id DESC;

SELECT id, display_name
FROM app_users
WHERE email = 'alex@example.com';

SELECT id, display_name
FROM app_users
WHERE display_name LIKE 'Al%'
ORDER BY display_name, id
LIMIT 20 OFFSET 0;
```

`%` means any sequence in LIKE; `_` means one character. User-entered literal search patterns may need escaping.
Pagination needs a deterministic ORDER BY; add an ID tie-breaker. Large OFFSET values can become expensive.

Create and practise on this separate table (prefer the practice database):

```sql
CREATE TABLE IF NOT EXISTS practice_notes (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    title VARCHAR(120) NOT NULL,
    done BOOLEAN NOT NULL DEFAULT FALSE,
    priority INTEGER NOT NULL DEFAULT 1 CHECK (priority BETWEEN 1 AND 5),
    due_date DATE
);

INSERT INTO practice_notes (title, priority, due_date)
VALUES ('Learn SELECT', 2, DATE '2026-09-10');

INSERT INTO practice_notes (title, done)
VALUES ('Start Spring Boot', TRUE), ('Read the local guides', FALSE);

SELECT * FROM practice_notes ORDER BY id;

UPDATE practice_notes
SET done = TRUE
WHERE title = 'Learn SELECT';

DELETE FROM practice_notes
WHERE title = 'Read the local guides' AND done = FALSE;
```

For the real app, create accounts through the registration form so validation, normalization, and hashing run.
An INSERT normally omits identity and defaulted columns.
Always preview an UPDATE/DELETE selection with SELECT and use a precise WHERE clause. Without WHERE, every row is affected.
Use IDs when possible; names/titles may not be unique.

## Conditions, NULL, and expressions

```sql
SELECT * FROM practice_notes
WHERE done = FALSE AND (priority >= 3 OR due_date < CURRENT_DATE);

SELECT * FROM practice_notes WHERE priority IN (1, 3, 5);
SELECT * FROM practice_notes WHERE priority BETWEEN 2 AND 4;
SELECT * FROM practice_notes WHERE due_date IS NULL;
SELECT * FROM practice_notes WHERE due_date IS NOT NULL;

SELECT title,
       COALESCE(CAST(due_date AS VARCHAR), 'No deadline') AS deadline,
       CASE WHEN done THEN 'Finished' ELSE 'Open' END AS state
FROM practice_notes;

SELECT LOWER(email), TRIM(display_name) FROM app_users;
```

NULL means missing/unknown. Use `IS NULL`, not `= NULL`.
`column <> 'x'` does not include NULL rows; add `OR column IS NULL` if needed.
`BETWEEN` includes both endpoints. Parentheses make AND/OR intent explicit.
`COALESCE(a, b)` chooses the first non-null value. `AS` assigns an output alias.

## Aggregation and grouping

```sql
SELECT COUNT(*) AS total FROM app_users;

SELECT done, COUNT(*) AS notes, MAX(priority) AS highest_priority
FROM practice_notes
GROUP BY done;

SELECT priority, COUNT(*) AS notes
FROM practice_notes
WHERE done = FALSE
GROUP BY priority
HAVING COUNT(*) >= 2
ORDER BY notes DESC;
```

`WHERE` filters individual rows before grouping. `HAVING` filters groups afterward.
`COUNT(*)` counts rows; `COUNT(column)` counts non-null values.
Common aggregates: `COUNT`, `SUM`, `AVG`, `MIN`, `MAX`.
Selected columns outside aggregate functions generally need to appear in GROUP BY.

## Relationships and joins

The following two tables are only for practice; they are not part of app registration:

```sql
CREATE TABLE practice_projects (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name VARCHAR(80) NOT NULL
);

CREATE TABLE practice_tasks (
    id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    project_id BIGINT NOT NULL,
    title VARCHAR(120) NOT NULL,
    CONSTRAINT fk_practice_task_project
        FOREIGN KEY (project_id) REFERENCES practice_projects(id)
);

INSERT INTO practice_projects (name) VALUES ('Website'), ('Garden');
INSERT INTO practice_tasks (project_id, title)
SELECT id, 'Create registration page'
FROM practice_projects WHERE name = 'Website';

-- Only projects that have tasks:
SELECT p.name, t.title
FROM practice_projects p
INNER JOIN practice_tasks t ON t.project_id = p.id;

-- All projects, including those with no tasks:
SELECT p.name, t.title
FROM practice_projects p
LEFT JOIN practice_tasks t ON t.project_id = p.id;

-- Count zero-task projects correctly:
SELECT p.id, p.name, COUNT(t.id) AS task_count
FROM practice_projects p
LEFT JOIN practice_tasks t ON t.project_id = p.id
GROUP BY p.id, p.name;

-- Projects with at least one task:
SELECT p.name FROM practice_projects p
WHERE EXISTS (SELECT 1 FROM practice_tasks t WHERE t.project_id = p.id);
```

A foreign key prevents orphan tasks. By default you cannot delete a referenced project until its tasks are handled.
Use `ON DELETE CASCADE` only when automatic child deletion is the intended rule.
Putting a condition on `t` in a LEFT JOIN's WHERE clause can filter out its NULL rows; place matching conditions in ON if empty parents should remain.

## Transactions

A transaction groups changes that must succeed or fail together.
In the H2 SQL shell, practice without committing a change:

```sql
SET AUTOCOMMIT FALSE;

SELECT id, title, done FROM practice_notes ORDER BY id;
UPDATE practice_notes SET done = TRUE WHERE title = 'Start Spring Boot';
SELECT id, title, done FROM practice_notes ORDER BY id;

ROLLBACK;
SET AUTOCOMMIT TRUE;
```

To save intended changes, use COMMIT instead of ROLLBACK, then restore autocommit.
Autocommit means each statement is committed independently.
Keep transactions short. Do not leave a transaction open while waiting for a human or a remote service.

H2 schema-changing commands commonly commit transactions themselves. Do not rely on ROLLBACK to undo CREATE/ALTER/DROP/TRUNCATE.
In Java, use Spring `@Transactional` on a service for multiple writes; see the Spring Boot cheatsheet.
The registration service owns a JPA transaction and flushes its INSERT before returning. Its UNIQUE constraint prevents races even if two requests reach it together.

## Indexes and performance

```sql
CREATE INDEX idx_practice_tasks_project ON practice_tasks(project_id);

EXPLAIN SELECT title FROM practice_tasks WHERE project_id = 1;
```

An index speeds suitable searches/joins/orderings but uses disk and adds work to writes.
Primary keys and unique constraints already have supporting indexes; do not duplicate them without a reason.
The app's unique email constraint supports exact normalized email lookup.
Functions such as `LOWER(email)` in predicates can prevent use of an ordinary email index; normalize consistently instead.
Select only needed columns and put limits on user-facing lists.
Parameter placeholders represent values, not table names, column names, or sort direction; allowlist any dynamic identifiers.

## Java and SQL together

This project's primary persistence path uses a JPA entity and repository:

```java
// UserRepository extends JpaRepository<AppUser, Long>.
users.saveAndFlush(new AppUser(displayName, normalizedEmail, passwordHash));
```

Hibernate generates the INSERT from `AppUser`'s mapping. Derived queries such as `findByEmail` use Java property names.
The [Spring Boot cheatsheet](spring-boot-cheatsheet.md#entities-repositories-and-transactions) covers entities, JPQL, relationships, and transactions.

If you deliberately need plain SQL, inject `org.springframework.jdbc.core.simple.JdbcClient` into a component and bind parameters:

```java
jdbc.sql("""
        INSERT INTO app_users (display_name, email, password_hash)
        VALUES (:displayName, :email, :passwordHash)
        """)
        .param("displayName", displayName)
        .param("email", email)
        .param("passwordHash", hash)
        .update();
```

Never construct SQL like `"WHERE email = '" + email + "'"`.
The driver binds each named parameter as data, including quotes and other SQL-like characters.
Named placeholders are supplied by Spring; to run the statement directly in the H2 shell, substitute deliberate SQL literals.
The JPA service catches `DataIntegrityViolationException`, recognizes the named email constraint, and converts only that conflict into a registration field error.

## Schema changes

Edit entity mappings and restart: Hibernate uses `ddl-auto=update` to create missing tables and apply supported schema changes.
Back up first. Automatic updates do not infer renames or data transformations and may not alter existing constraints. Use a deliberate migration for those changes, and keep entity mappings consistent.

Practice example:

```sql
ALTER TABLE practice_notes ADD COLUMN description VARCHAR(500);
UPDATE practice_notes SET description = '' WHERE description IS NULL;
ALTER TABLE practice_notes ALTER COLUMN description SET DEFAULT '';
ALTER TABLE practice_notes ALTER COLUMN description SET NOT NULL;
```

For a real application, keep numbered migration files and record which have run, preferably using a migration tool such as Flyway or Liquibase.
Do not mix multiple competing schema managers. This learning project uses Hibernate `ddl-auto=update` and disables SQL initialization scripts. If adopting Flyway or Liquibase, switch Hibernate to `ddl-auto=validate` so migrations own schema changes.
When switching to PostgreSQL/MariaDB, add its JDBC driver, configure its URL/credentials, and adapt/test identity, timestamp, and migration SQL.
Changing DB_URL alone does not copy existing H2 data into the new database.

## Back up and restore

Simplest file backup: stop the app and every H2 shell, then copy `data/project11.mv.db` to a backup location.
Preserve the original database when deploying a new JAR. Do not copy a live database file as a backup.
The [Pi guide](raspberry-pi.md) includes commands for a stopped service backup.

For a logical SQL export, with only your local shell connected and an existing `backups` directory:

```sql
SCRIPT TO 'backups/project11.sql';
```

This export contains user data and password hashes. Protect it like the database.
Restore into a new, empty database opened with a different URL:

```sql
RUNSCRIPT FROM 'backups/project11.sql';
```

Use a compatible H2 version and the database's original credentials when reconnecting. Verify row counts and sample records before replacing a live database.
Backups are useful only if you can restore them; practise on a copy.

## Common errors

| Error | Meaning / fix |
| --- | --- |
| Table not found | Wrong database URL, schema not initialized, or quoted case mismatch |
| Unique constraint violation | Duplicate value; handle as an expected conflict |
| Foreign key violation | Parent missing or still referenced by child rows |
| Value too long | Validate input or deliberately migrate the column |
| Database already in use | Another JVM/shell owns the embedded file; stop it |
| Wrong username/password | Existing file retains the credentials used when created |
| Syntax error near USER | Reserved identifier; this app uses `app_users` |
| Empty query unexpectedly | Check normalization, NULL logic, transaction commit, and file path |

Optional reference: [H2 SQL commands](https://h2database.com/html/commands.html).
